# Operations and security

## Before business use

This application is intended for supplies and equipment. Keep patient identifiers, clinical notes, and other patient information out of inventory names, references, and audit details. Medication dispensing, controlled-substance controls, and healthcare compliance certification are outside this version. If the business needs those capabilities, define the data and access requirements before introducing that data.

Confirm domain/TLS setup, staff access, backup restoration, network-policy enforcement, monitoring ownership, and deployment/rollback procedures in the actual AWS account. Account-level agreements, policies, and organizational controls are not created by source code.

## Daily operation

- Create one item per SKU and choose the unit deliberately (box, pack, each, etc.). Receipts and issues use that unit.
- Record opening quantities with a receipt and a useful operational reference.
- Use transfers for movement between locations; stock stays constant across the organization.
- Use signed adjustments for stock-count corrections. Only managers/admins can adjust stock.
- Purchase orders are drafts until marked ordered. The app does not email or send them to suppliers. Receiving adds every order line in full; partial receipts are not available.
- Low-stock flags use total quantity at or below the catalog reorder point, including items with no stock yet.
- Dashboard valuation multiplies catalog cost by current stock; order costs remain on the order and do not change catalog cost.
- Disable departing staff accounts promptly. Existing sessions are revoked. Every staff member should use their own account.

## Observability

```bash
kubectl -n goshenignite get pods,deploy,svc,ingress,hpa,pdb
kubectl -n goshenignite logs deployment/backend --tail=100
kubectl -n goshenignite logs deployment/frontend --tail=100
kubectl -n goshenignite get events --sort-by=.lastTimestamp
kubectl -n goshenignite get externalsecret inventory-db
helm -n goshenignite history inventory
```

The API exposes liveness and database readiness endpoints. EKS control-plane logs retain 90 days. RDS exports PostgreSQL and upgrade logs. A low-free-storage alarm publishes to the Terraform-created operations SNS topic; add and confirm an operational subscription in your account. No alert recipient is configured by default. Container logs are available through kubectl; centralized container log shipping, uptime alerts, error-rate alerts, and a dashboard stack still need your observability platform configured.

Login rate limiting is in process and therefore per API replica. Put a centralized rate limit/WAF policy in front of the application if that is needed for public deployment. Password reset is an operator task in this version; there is no recovery email workflow, MFA, or SSO.

## Backup and recovery

RDS has encryption, Multi-AZ failover, automated backups retained for 14 days, deletion protection, and a required final snapshot. Multi-AZ availability does not replace backups.

Perform a restore exercise before relying on this deployment:

1. Restore a point-in-time or snapshot copy into isolated database subnets with the database security group.
2. Verify the restored schema, staff records, stock totals, movements, and orders from a controlled application instance.
3. During an incident, stop writes before choosing a recovery point. Record the accepted data loss window.
4. Update the managed infrastructure and application database secret to the restored endpoint; reconcile Terraform intentionally rather than leaving drift.
5. Wait for External Secrets synchronization, restart backend pods, verify readiness, and run representative workflows.

Backups contain user hashes and operational business records. Restrict backup and restore permissions. Define business RPO/RTO targets and test whether the selected instance sizes and procedures satisfy them.

## Secrets and password rotation

Never commit `.env`, Terraform state/plan files, real `.tfvars`, private keys, or credentials. The application database password is generated by Terraform and consequently also appears in protected Terraform state. The RDS master secret is AWS-managed and not injected into normal app pods.

Application database password rotation is a coordinated maintenance operation: update the generated secret, provision the corresponding database role password with the operator job, force External Secrets reconciliation or wait for its refresh, and restart the backend. Existing pods do not automatically reload environment variables when a Secret changes. Account for an interruption during a single-password rotation; implement a dual-user rotation strategy if uninterrupted rotation is required.

API audit events are append-only through the API, but the application's database owner can modify them. They are not independently tamper-proof records. Database administrative access must remain restricted; export audit events to separately protected storage if required.

## Rollback

```bash
helm -n goshenignite history inventory
helm -n goshenignite rollback inventory PREVIOUS_REVISION --wait --timeout 10m
```

Rollback changes Kubernetes resources/images, not SQL schema or data. Keep migrations compatible with the previous app release. Destructive data changes need a deliberate backup, migration, and restoration strategy. ECR retains tagged images so previous releases remain available; only old untagged images are automatically expired.

## Common failures

| Symptom | Check |
| --- | --- |
| Docker daemon connection error | Start Docker Desktop with Linux containers. |
| Sign-in fails locally | Seed the database, check configured email/password, and use `http://localhost:8080` exactly. |
| API rejects request origin | Match `APP_ORIGIN` to the browser URL; production requires HTTPS. |
| Migration pod waits for a secret | Check External Secrets controller IRSA, secret ARN, store status, and namespace. |
| Migration fails connecting to RDS | Run database provisioning first; check TLS CA, network policies, database security group, secret, and role. |
| Private deployment runner cannot connect | Confirm VPC routing, DNS, private EKS access, and deploy-role access entry. |
| ALB is missing or unhealthy | Check controller logs, subnet tags, IAM, ACM region, target pods, and frontend readiness. |
| Helm fails a migration | Inspect `job/inventory-migrate`; fix the migration before retrying. |
| Duplicate manual stock movement after retry | Inspect ledger and perform a documented manager adjustment if needed; general manual movements do not have idempotency keys. |

## Capacity and planned extensions

This version loads the entire item catalog and caps recent ledger/order/audit views at 200 rows. Add server pagination, query indexes, export jobs, and load tests as the catalog and history grow. The HPA scales API pods but no node autoscaler is installed; adjust the managed node group's capacity or install your chosen autoscaler before depending on automatic node growth. Workload resources and two-node defaults need measurement under real usage.

Prioritize requirements for location-specific thresholds, asset serial numbers, barcode scanning, expiry/lot tracking, purchase approvals, partial receiving, supplier communications, and SSO. Each affects workflow and data design; these are not claimed as implemented.
